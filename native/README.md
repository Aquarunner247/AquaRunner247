# The React Native shell

Phase 2 of [`NATIVE-REBUILD-PLAN.md`](../NATIVE-REBUILD-PLAN.md). One WebView over
`https://aquarunner247.com`, plus a bridge that gives the page the hardware it needs.

**This is not a port.** The binary contains no app logic — all ~68k lines of `app/` and `lib/` are
still server-rendered Next.js, exactly as under Capacitor. What changes is that the shell is ours,
so Phase 3 can replace one technician screen at a time with native views while every screen that
is not ported keeps rendering in the WebView.

The Capacitor shell at the repo root is still the one that ships. Both exist until Phase 4.

## Why a bridge had to be built first

Capacitor injects `window.Capacitor` into its WebView and the page talks to its plugins through
it. React Native injects no such thing. So on the day the shell changes, every
`Capacitor.isNativePlatform()` in the web app goes false and **the app silently degrades to
browser behaviour** — no background location watcher, no OS camera, no hardware back. Nothing
throws and nothing logs.

That was measured, not predicted: the first build of this shell loaded the live site and the
hardware back button did nothing at all, because production was still running the old page code.

The fix is four modules, three of them in the web app's `lib/` so the test suite reaches them:

| Module | Side | What it is |
| --- | --- | --- |
| `lib/native-bridge-protocol.ts` | both | The capabilities, the envelopes, the parsers, the origin-trust rule |
| `lib/native-bridge-client.ts` | page | Correlating calls to replies, routing watcher events |
| `lib/native-bridge-host.ts` | shell | Who may ask, and what a failure looks like to the page |
| `lib/client/native-host.ts` | page | The only file in the app that imports `@capacitor/*` |

`native/src/capabilities.ts` is the only part that touches hardware, and is deliberately thin:
anything that can be reasoned about lives on the other side of that line, under test.

## Building

Needs JDK 21 and the Android SDK with platform **37** (`compileSdk` 37 — Expo SDK 58's modules
require it; `targetSdk` stays at 36 to match the Capacitor build's runtime behaviour).

```bash
cd native
npm install
npm run prebuild                 # regenerates android/ and ios/ from app.config.ts
JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64 ./android/gradlew -p android assembleRelease
```

`JAVA_HOME` on the command line rather than `org.gradle.java.home` in `gradle.properties`: that
file is regenerated by every prebuild, so an edit there does not survive — and the path is
machine-specific anyway, same reason the Capacitor project's copy is not committed.

**`android/` and `ios/` are not committed.** They are generated from `app.config.ts`, and the repo
root already has an `android/` (the Capacitor shell's). Two committed native directories is how
somebody signs a release from the wrong one.

### Pointing it at a local server

```bash
AQ_WEB_URL=http://10.0.2.2:3979 AQ_ALLOW_DEV_ORIGIN=1 npm run prebuild
```

One switch, not two: `AQ_ALLOW_DEV_ORIGIN` turns on both cleartext HTTP and the bridge's trust of
a localhost origin, so neither can be enabled alone and a shipped build has neither.

Note that `next start` sends `upgrade-insecure-requests` in its CSP, which over plain HTTP rewrites
every stylesheet and script to `https://10.0.2.2:…` and loads nothing. Testing the real page
locally means stripping that one directive in front of it. A service worker will not register over
HTTP either (no secure context), so **the offline shell cannot be exercised this way** — it needs a
real HTTPS deployment.

## What has been verified, and what has not

Verified on an Android 37 emulator with a release APK:

- Builds, installs, launches, renders the live production site with correct safe-area insets.
- **The bridge round-trips.** A hardware back press reaches the shell, is emitted to the page, the
  page decides the screen is a home screen, calls `app.minimize`, and the shell backgrounds the
  app — with the process still alive, so an unsaved reading survives. That one press exercises the
  injected bootstrap, host detection, event delivery, a page→shell call, origin trust and a
  capability.
- **No new permissions.** The release manifest asks for exactly what today's bundle asks for,
  minus `ACCESS_NETWORK_STATE` and `WAKE_LOCK`, which the Capacitor build only has because
  `@capacitor/push-notifications` drags in Firebase for a permission prompt it never registers
  with. Pinned by `lib/__tests__/native-shell-config.test.ts`.
- The shared `lib/` modules bundle in, and no web-only code follows them (`PrismaClient`,
  `next/navigation`, `leaflet`: zero occurrences in the bundle).

Not verified, and needing a device or a real deployment:

- **The camera, the one-shot position and the background watcher.** An emulator has no camera and
  a synthetic GPS; the watcher's whole point is a phone in a pocket between stops.
- **Whether background fixes keep arriving with the screen off.** Both shells declare
  `foregroundServiceType="location"` and neither holds a wake lock, so there is no reason to
  expect a difference — but the departure-detection work this project started from means this is
  the one behaviour worth measuring rather than assuming.
- **The offline recovery to `/field`,** for the service-worker reason above.
- **iOS.** Configured, never built. No Apple hardware here, and enrollment `9AJDVC9VDW` is still
  pending.
